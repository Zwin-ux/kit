# Kit Red: product and design specification

> Superseded release organization: the user requested V1 visual-only, then V2 integration. Use [the versioned build pack](../../kit-red/README.md) as the implementation entry point; retain this combined document as planning history.

Date: 2026-10-01
Status: proposed implementation scope; documentation only, no mod built or installed.

## Objective

Make Kit recognizable as a red, fox-branded workspace inside Claude Code, with useful access to installed kits, agent readiness, runs, and actual check results. Carry the same red identity into Kit's standalone terminal UI. Keep Kit open source under its existing MIT license.

User direction: “Claude Code red” is the overall visual direction, with functional improvements. This means a cohesive red identity across supported UI surfaces, not a wall of red text.

## Evidence and working assumptions

- Upstream reviewed: Zwin-ux/kit commit `c35f60855a62534f2ed71edac3d1dc52835b87a3`.
- Local checkout inspected: `/Users/entreprenurecosystem/kit`, commit `fb0ddf198256940fc243c8f23318c27d6ff1ea87`; it is older than upstream. Do not implement against its obsolete package names or overwrite its existing task history.
- Current upstream Kit uses a Rust engine, a terminal Control Room, and CLI JSON envelopes. Upstream already has light/dark palettes, a fox mark, and a fox-orange accent (`#FF5A1F` dark, `#E04814` light). This feature shifts the primary identity toward red rather than recreating the UI.
- Claude Code installed on this Mac reported `2.1.287`, the documented minimum for mods. Interactive compatibility has not been tested.
- A mod adds supported render sites and commands. It cannot globally recolor every host element, change the permission prompt, or turn proprietary Claude into an open-source model.
- Primary acceptance target: Claude Code terminal. Secondary: Code tab in Claude Desktop. VS Code chat, headless, and cloud surfaces need text fallback where commands are available; no promise of visual theming there.
- Keep standalone Kit and its Codex/Grok support. The mod is another frontend over the existing engine.

## Approach

Choose one plugin, `kit-red`, with a visual mode that works without the Kit binary. When Kit is available, the same plugin exposes its capabilities through `/kit`.

Alternatives considered:

| Approach | Tradeoff | Decision |
| --- | --- | --- |
| Visual-only plugin | Small and useful, but no access to Kit workflows | First milestone |
| Visual plugin plus Kit CLI integration | Reuses existing behavior and gives a useful Control Room inside Claude | Target product |
| Fork Claude or replace Kit with a new JavaScript engine | Large maintenance burden and duplicated behavior | Excluded |

No daemon, HTTP server, new database, custom model, or generic theme framework. Mod code uses Claude's supplied API and local modules. Rust remains responsible for installations, worktrees, agents, checks, receipts, and landing.

## Visual system

Proposed semantic tokens, finalized through real terminal captures:

| Role | Dark surface | Light surface | Usage |
| --- | --- | --- | --- |
| Kit red | `#FF5A5F` | `#B42332` | Kit title, active tab, selected action, fox accent |
| Main text | `#F4F1ED` | `#242124` | Readable content, never all-red body text |
| Secondary text | `#AAA3A5` | `#62595C` | Metadata, age, shortcuts |
| Soft selection | `#321C22` | `#FBE9EC` | Kit-owned selected rows; pair with a text/shape cue |
| Live activity | `#53D6CF` | `#006B67` | Confirmed RUNNING text, separate from brand and error red |
| Success | `#74D99A` | `#176B3A` | Check passed, with explicit PASS text |
| Warning | `#F2C66D` | `#805500` | Missing setup, stale data, unconfigured checks |
| Failure | `#FF8D96` | `#A0152B` | FAIL/ERROR labels and error details |

Inherit the terminal background by default. Explicit dark/light/high-contrast/monochrome modes handle terminals whose background cannot be inferred reliably. Do not mutate the user's terminal palette or host theme settings.

Use Kit's existing fox asset as the identity. Render a compact text mark (`KIT`) as the baseline; add the fox through supported drawing only if it stays crisp at terminal cell sizes. Desktop gets portable elements; terminal-only artwork is optional.

Reference backgrounds for contrast checks are dark `#151214` and light `#FFF8F6`; they are test fixtures, not forced terminal colors. All listed text colors must meet 4.5:1 against those reference backgrounds. Inherited backgrounds and ANSI palettes need separate captures and user overrides.

Red is the dominant accent across titles, tabs, the compact band, and Kit actions. Preserve distinct running, checking, success, failure, and unavailable labels. Color must never be the only distinction.

Respect `NO_COLOR` and `KIT_MOTION=off`. No continuous mascot animation in the first release. Never hide host status text, tool arguments, errors, or permission decisions to achieve a theme.

## Supported surface contract

| Surface | Intended change | Preservation rule |
| --- | --- | --- |
| `AbovePrompt` | Compact red Kit mark, local session activity, latest check summary | Compose the downstream tree so other mods remain visible; no hotkeys that consume normal typing |
| `Pane` | `/kit` Control Room, tabs, details, keyboard actions | Render only the `kit-red` pane; other panes pass through |
| `Spinner` | Red Kit working treatment | Prefer a red adjunct composed with host drawing; retain all host information including elapsed time, tokens, and effort, which may not be exposed in Spinner props |
| `PromptHint`, `SessionMode`, `TurnDuration` | Optional red accents where a safe adapter preserves content | Feature-by-feature compatibility proof; otherwise leave host drawing intact |
| Messages and tool rows | Neutral, readable existing output | No broad replacement in this release |
| Permission prompt and native prompt editor | Host-controlled | No replacement or claim of full recoloring |
| Standalone Kit | Apply the same tokens to existing theme and brand functions | Preserve semantic state colors, existing light/high/mono modes, geometry, and one-clock motion rules |

If a host site cannot be recolored without losing meaning, retain it. Document precisely which parts are styled; never advertise a complete host skin based only on a red banner.

## Main experience

`/kit` opens a pane with three tabs: Overview, Kits, Runs. It does not start an agent or model turn. Esc closes it; Tab and explicit button hotkeys navigate it. At narrow widths it becomes stacked content above the prompt.

Text wireframe; proposed appearance, not a screenshot:

    KIT / current-repo                      Updated 8s ago
    [Overview]  [Kits]  [Runs]

    Claude Code     Detected; launch not tested
    Kit             CLI available
    Checks          Configured

    Latest run      Fix form validation
    Result          FAIL — typecheck
    Next            Read check details

    [Refresh]   [View run]   [New run]

### Overview

Show repository, Kit version, exact agent probe result, installed-kit count, latest relevant run, data age, and next action. Distinguish detected, authenticated if actually probed, and proven launchable; never collapse them into an unsupported Ready claim. Treat a plain Claude session as “This session”; never associate its edits with an unrelated Kit receipt.

Show “Kit is not installed” with an explicit installation command when missing. The visual theme continues working. Report malformed output, timeout, unsupported schema, and permission refusal as actionable connection states.

### Kits

List actual installed kits with project/global scope, relevant agent, and modified-file warnings. Show metadata from Kit, not a hard-coded product catalog. Initial integration is read-only with exact CLI handoff commands for add/remove.

The subsequent management slice offers preview → confirm → execute → refresh for add/remove. Preview must include scope, file changes, source/revision, license, code-running hooks/MCP entries, and manual-edit conflicts, matching Kit's existing behavior. Default to this project and Claude only. Keep a skills/rules-only option.

The current remove CLI has no preview flag, and a metadata-only branch can write before its confirmation. Never call remove as an inspection operation. Build a true no-write preview first.

No `--force`. No implicit global installs. A stale preview must be regenerated. Do not treat a named remote source as pinned; execute only the same resolved content reviewed by the user. If the existing CLI cannot bind preview to execution, the management slice must add that narrow contract before enabling the button.

### Runs

List receipts for the current repository by default, newest first, with an explicit “All projects” filter. Show state, agent, task, actual check result, timestamp when present, and freshness. A list entry is evidence of a stored run, not proof that its process is still alive.

Run detail shows check count/outcomes, receipt ID, repository identity, recorded base/tested commit when available, completion time, first failure, changes, and output tail only on request. A PASS says “N/N configured checks passed,” not “safe” or “ready to merge.” Do not invent a tested commit when the receipt cannot identify it. Preserve warnings and truncated-output labels. Cap rendered rows at 50; indicate that more history exists. Current CLI rows use repository basenames and global limits. Add canonical `repoPath` identity and filtering before limiting; two unrelated repositories with the same basename must never mix. Add `hasMore` instead of inferring total history from returned row count.

Distinguish PASS, FAIL, RUNNING, CHECKING, UNCONFIGURED, NO CHANGES, KILLED, ERROR, and UNKNOWN where authoritative data supports them. Never infer PASS from exit code alone or from the model's completion message. Old receipts without adequate proof show UNKNOWN/UNCONFIGURED.

### Actions

- New run: enter task, choose a ready agent, review repository and committed base, then start via Kit. Explain that uncommitted edits are not included. Prevent duplicate submission. Bind the reviewed committed base and check plan to launch in the engine; a changed HEAD or gate configuration requires renewed review before worktree creation.
- Retry: creates a new run, linked visibly to the previous run, with task and failure context available for review. No automatic retry loop.
- Create result branch (Kit land): review the receipt and changes, then create Kit's normal result branch. Revalidate the reviewed receipt/diff and expected result-branch inputs before mutation. No force, apply-to-dirty-tree, automatic merge, push, or PR publishing.
- Stop: expose only after cancellation is proven to stop the owned run and its child agent, preserve a final receipt, and leave unrelated sessions alone. Do not implement as “close pane.”

Run launching is a separate release gate: nested Claude execution, approval handling, process lifecycle, and child cleanup must be demonstrated. Never set `KIT_FULL_AUTO=1` to make the integration appear to work. If an adapter cannot obtain required interaction, disable its launch action and show the supported terminal command. The standalone Control Room remains available.

## Architecture and data flow

    Claude Code mod UI
       → bounded argv calls through $.process
       → existing Kit CLI JSON contract
       → existing Rust engine / installation logic
       → existing Kit receipts and records
       → validated view data back to the pane

Use the current JSON envelope (`schemaVersion`, `command`, `ok`, `data`, `error`, `warnings`). Inner receipt detail currently uses Rust snake_case and SystemTime values, unlike the envelope; normalize the actual shape rather than assuming every field is camelCase. Validate version, types, nullable error/data, and command identity. Preserve semantic failure data even if the command exits nonzero.

Known current entry points: `kit list --json`, `kit receipt list --json`, `kit receipt show <id> --json`, `kit run --task <text> --agent <agent> --json`, `kit land <id> --json`. `kit list --json` already returns both scopes in `data.scopes`; each includes installed `kits` and `notInstalledHere`, and kit rows include `drift`. No second global read is needed. Details live in the integration review linked below.

**Required passive diagnostics change:** current `kit doctor --json` executes configured kit check commands even without `--start-mcp`. Never run it automatically on pane open/refresh. Add `doctor --passive --json` (proposed) that performs config/file inspection only, skips custom checks and MCP startup, and marks those results not run. Automatic diagnostics also must not run arbitrary agent binaries: presence/version/auth execution is a separate explicit probe unless an existing passive source establishes it. Inspection errors remain visible, not converted into empty success.

**Required module shape:** all mods API calls and helpers receiving `$` stay at top level in `hooks/register.js`. Claude’s static validator forbids passing `$` to imported helpers or aliasing its namespaces. Separate modules may only hold pure parsing, formatting, state transitions, and element-tree construction given already-resolved primitives.

Always pass an argv array, never concatenate a shell command. Resolve repository scope explicitly; do not depend on whatever directory a terminal happens to be in. Use a trusted installed Kit binary, not a repository-provided executable. No automatic dependency downloads from UI rendering.

Read operations: 10-second deadline, single in-flight refresh, manual refresh initially. Never spawn a process from a render handler. Cache view data in session memory, preserve the last good result as visibly stale after a failure, and reject obsolete refresh responses. Theme settings can use the plugin store; receipts remain in Kit.

Stored receipts are published after completion and cannot supply a live feed. If live launch ships, add an opt-in structured engine-event stream while keeping existing final JSON behavior.

Add periodic refresh only while an observed run is active and the pane is visible, at most every 5 seconds. No background polling for a closed pane or headless session. Cross-session process recovery requires authoritative engine state; it cannot be reconstructed from a timestamp. Until ownership is recovered, show “Last recorded: RUNNING; current activity unknown” and disable Stop.

Lifecycle: `session.start` handles startup/reload; `classic.SessionStart` with clear/resume/fork refreshes settings and resets scope/selection/refresh generations. `ui.close` cancels pane refresh. Timers stop on reload, but child-process-tree cleanup is not guaranteed by that fact. Never rely on the short session-end hook deadline for durable receipts. No duplicate launch after reload.

Interactive `/kit` returns `{}` so opening the pane does not publish receipt content into the model transcript. Explicit text fallback is bounded and documented as model-readable. A process call does not inherit a model Bash confirmation prompt; the plugin’s review action is its mutation boundary and managed denials must be honored.

Treat agent output, task titles, repo paths, and receipts as untrusted display data: bound length, remove unsafe terminal control sequences, and never interpret their contents as commands. Viewing a receipt does not inject it into the conversation or start a model call.

## Packaging and open source

Directory: `mods/kit-red/` within the existing Kit repository. One plugin; no second npm package required. Keep the root MIT license and include plugin redistribution/license instructions. Use the existing Kit fox, with attribution review for any additional assets.

The plugin can run its visual layer independently. Integration requires a compatible Kit CLI; source tests and a documented version matrix determine the supported floor. Record the exact tested Kit and Claude versions in the release README. Official GitHub type declarations inspected during review are older than the installed CLI; generated declarations from the actual build take precedence. Desktop UI portability and Desktop access to Kit/checkouts are separate tests. Desktop WSL currently lacks plugin support.

After local proof, add a repository plugin marketplace entry and a tagged release. Document installation, `/reload-plugins`, disabling, and uninstalling. Disabling restores host UI and stops plugin activity; Kit's own installed kits and receipts remain intact.

## Success criteria

1. A real terminal session visibly reads as Kit Red across the band, pane, and supported working/status treatments, with consistent standalone Kit branding.
2. `/kit` works without an API/model call and remains usable when Kit is missing or errors.
3. Installed kits and receipts match the CLI for the selected repository and scope.
4. A real failed run exposes its failed check; a real passing run displays proof; empty checks never become PASS.
5. Management and run actions preserve Kit's ownership, review, and rollback semantics. No hidden approval bypass.
6. Keyboard-only operation works at 60×20, 80×24, and 120×40; light/dark/high/mono and reduced-motion paths are tested.
7. Desktop portable elements are checked separately; unsupported visual surfaces return concise text.
8. Reload, disable, uninstall, missing binary, corrupted JSON, wrong schema, duplicate clicks, and interrupted runs have verified outcomes.
9. Public documentation and recordings distinguish mocks from real runs. No release claim based solely on unit tests.
