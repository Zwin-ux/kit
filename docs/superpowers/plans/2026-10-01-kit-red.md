# Kit Red Implementation Plan

> Superseded release organization: the user requested V1 visual-only, then V2 integration. Use [the versioned build pack](../../kit-red/README.md) as the implementation entry point; retain this combined document as planning history.

> **For agentic workers:** Use `executing-plans` task by task, or user-authorized `subagent-driven-development` with independent review. Follow the current Kit `AGENTS.md` ownership rules. Steps use checkboxes for tracking.

**Goal:** Deliver a red Kit identity inside Claude Code and in standalone Kit, then connect real kit management and verified agent workflows.

**Architecture:** One Claude plugin calls the existing Rust CLI through bounded argv-based process calls. Kit retains ownership of installations, execution, checks, and receipts. The visual layer works even when Kit is unavailable.

**Tech stack:** Claude Code mods API; JavaScript ES modules; Claude's built-in `.test.ts` runner; current Rust workspace and existing tests. No new runtime dependency or service.

**Specification:** [Kit Red product specification](../specs/2026-10-01-kit-red.md).

**Status:** Planning deliverable, not implementation. Source contracts below describe intended additions where marked “proposed.” Every release requires live evidence as well as mocked tests.

## Global constraints

- Minimum documented Claude Code version: `2.1.287`; test exact versions before release.
- Build from current upstream, not this older local checkout. Preserve existing uncommitted work and task history.
- Plugin directory/name: `mods/kit-red/`, `kit-red`; command: `/kit`.
- Prefer existing Kit JSON commands; maintain `schemaVersion: 1` for additive compatible fields.
- Never pass `$` into an imported helper, alias its namespaces, or use dynamic hook names/imports. Pure view functions receive resolved element functions and data, not `$`.
- No Node imports in mod runtime. Use literal `$.process`, `$.env`, `$.store`, and `$.ui` calls so static capability analysis works.
- Never spawn processes in render handlers; never interpolate shell commands.
- No credentials, telemetry, automatic model requests, prompt rewriting, or permission override hooks.
- `NO_COLOR`, `KIT_MOTION=off`, keyboard access, clear proof state, and exact uninstall behavior are required.
- No automatic merge, push, force-install, force-land, or full-auto agent approval.
- Visual target is all supported Kit surfaces; host-only regions retain Claude behavior.

## Delivery map

| Release slice | User value | Dependency | Independent acceptance |
| --- | --- | --- | --- |
| A: Kit Red | Cohesive red band/pane/working treatment and standalone theme | Capability proof | Real terminal captures and disable restores host |
| B: Kit Companion | Installed kits, readiness, actual run evidence inside `/kit` | A, JSON bridge | Display matches real CLI data and failure states |
| C: Kit Actions | Reviewable install/remove, run/retry/stop/land where supported | B, transaction and lifecycle proof | Real success/failure/cancellation without bypass |
| D: Open-source release | Reproducible install, documentation, compatibility matrix | Accepted slices | Clean-machine installation and independent replay |

A and B can ship while C is being proven. C is in the target scope, not silently cut. An unsupported action stays disabled with an honest terminal handoff until its proof gate passes.

## Task 3: Read Kit data safely

**Files:** pure `hooks/kit.js`, API-owning `register.js`, `view.js`, `tests/kit.test.ts`.
**Consumes:** current CLI envelopes; session working directory; trusted binary.
**Produces:** proposed top-level `readKit($, {cwd, argv})` in `register.js`, never imported, returning `{kind, data, warnings, observedAt, message}`; `kind` is `ready`, `missing`, `timeout`, `incompatible`, or `error`.

- [ ] Write one table-driven test for: good envelope, nonzero semantic failure, malformed JSON, wrong schema, wrong command, absent binary, timeout, and null data.
- [ ] Call the trusted executable via `$.process.run(argv, {cwd, timeoutMs:10000})`; use the exact signature in local declarations. Preserve exit code and structured error independently.
- [ ] Reject unknown schemas, wrong command names, and missing required fields. Do not scrape styled terminal text as structured data.
- [ ] Add a refresh generation counter and a single-flight guard so a slow older request cannot overwrite a newer repository/scope selection.
- [ ] Bound response size before parsing; initial ceiling 2 MiB. Bound displayed text and strip terminal control sequences. Oversized results show a clear error, not a hung pane.
- [ ] Retain the previous good response on refresh failure, marked stale with age and a retry action.

**Acceptance:** missing Kit does not break the red theme; repainting a pane never runs processes; opening may request only explicitly passive data through a command handler; no output becomes executable input; no process runs in headless mode just because the plugin loaded.

## Task 7: Prove process lifecycle before embedding runs

**Files:** `actions.js`, `actions.test.ts`, new lifecycle evidence document; engine/CLI changes only after identified gaps.
**Consumes:** `$.process.spawn`, current Kit runner/supervisor, current agent adapters.
**Produces:** tested launch/observe/stop contract or explicit adapter-specific terminal handoff.

- [ ] Trace CLI spawn → runner → adapter child → checks → receipt. Record who owns cancellation and what survives host reload, pane close, terminal exit, and interruption.
- [ ] Run the smallest real Claude task from the intended host context in a disposable repository. Detect nested-session refusal and approval waiting; do not unset protective variables or enable full auto.
- [ ] Repeat for each agent advertised as launchable. Grok currently requires full-auto in Kit, so it must remain terminal-handoff under this plugin policy unless that adapter gains an approved safe interaction path. A login probe is insufficient.
- [ ] Add opt-in JSONL events derived from existing `RunDelta` for run ID, sequence, lifecycle state, and final result; preserve current `run --json` final-envelope contract. Current stderr progress is unstructured and receipts publish after completion. Use the existing cooperative cancellation path; there is currently no cancel subcommand. A new control transport is justified only if the mods API cannot signal the owned process correctly.
- [ ] Verify run child processes terminate on accepted cancellation and a terminal receipt records the outcome. Never use a broad process-name kill.
- [ ] Pick and document host-exit behavior from observed platform support. If durable independent supervision is required but unavailable, retain terminal dispatch; do not fake background persistence.

**Gate:** Do not enable New run, Retry, or Stop for an adapter until its lifecycle evidence passes. A nested Claude limitation is a product constraint, not a reason to bypass approval controls.

- [ ] Preview repository, committed base, agent, checks, and uncommitted-work exclusion. Make New run an explicit user action. Test both races without starting an agent.
- [ ] Preserve the running operation across pane closure; show lifecycle state from the engine. Disable duplicate launch/stop/land actions while pending.
- [ ] Retry starts a distinct run after showing the task and selected failure context. Persist retry parent ID through a small engine-owned sidecar/contract if the link must survive reload; never infer it from task similarity. Do not automatically execute text suggested by agent output.

**Acceptance:** one real run fails checks, retry passes, land creates the reported branch; cancelling stops only its own work; dirty working copy is preserved; terminal-only fallback stays actionable for unsupported agents.

## Swarm execution boundaries

Use independent agents for (1) mod visuals, (2) CLI contracts, and (3) verification/security review after the shared contract is frozen. The coordinator owns integration and resolution of disagreements. Do not let several agents edit `register.js`, `cli.rs`, or the same task checklist simultaneously.

Respect the existing TUI/engine/contract ownership rules or obtain an explicit ownership change before implementation. Reviewers can inspect all code. The current planning swarm is read-only; its reports are inputs, not proof of implemented behavior.

## Deliberately excluded

A new model, Claude fork, hosted dashboard, marketplace social features, automatic agent swarms from opening `/kit`, chat synchronization, broad transcript replacement, decorative perpetual animation, and a second worktree/check engine. Add these only through a separate justified scope decision.

## Independent review acceptance

The review bundle is linked from the product spec. Accepted P0 corrections: passive diagnostics; canonical repo identity/filtering; validator-compatible module structure; preserved host Spinner status. Accepted P1 corrections: zero-write remove preview; reviewed-plan binding; mixed JSON detail shapes; explicit UI/conversation lifecycle. Accepted P2 corrections: structured live events and cooperative owned-process stop before run actions.

Each implementation task must map to the design review's journey/state matrix. Evidence records must include tested versions, command, observed result, and artifact path. A source audit, mocked test, real CLI run, and real host interaction are four different proof levels; do not substitute one for another.
